# v0.6.15 — V4 storage XML parsing + per-refresh diagnostic summary

User reported post-v0.6.14 (2026-09-25 07:30+): on the V4 DVR
(`DS-7708N-I4`, V4.1.18 firmware, `deviceType=DVR`):
- **Working**: model, serial number, channel count (from deviceInfo + channels list)
- **Unknown (still)**: every other sensor — CPU, memory, uptime,
  storage, network, per-channel health

The pattern — "deviceInfo works, channels work, everything else
unknown" — is consistent with the V4 firmware not implementing
V5's `DeviceStatus` schema but having a different
`Storage/hardDisks` schema we didn't parse.

## Root cause #1 — V4 storage XML uses `<hddList><HDD>` schema

V4 NVR/DVR firmware returns storage XML with a different shape
than V5:

```xml
<Storage xmlns="...">
  <hddList>
    <HDD>
      <id>1</id>
      <size>2000396746752</size>          <!-- BYTES, not MB -->
      <freeSize>1234567890123</freeSize>  <!-- BYTES -->
      <status>normal</status>
    </HDD>
    <HDD>
      <id>2</id>
      <size>4000796746752</size>
      <freeSize>...</freeSize>
      <status>exception</status>
    </HDD>
  </hddList>
</Storage>
```

Pre-v0.6.15 the parser only read V5's `<totalCapacity>` /
`<usedCapacity>` / `<freeCapacity>` (MB). When V4 firmware
returned the `<hddList>` shape, every field was `None`. With the
per-endpoint fault-tolerance of v0.6.14 in place, the refresh no
longer failed entirely — but the four storage sensors
(存储总量 / 存储使用量 / 存储剩余 / 存储使用率) silently showed
"Unknown" because `storage["total_mb"]` etc. were all None.

## Root cause #2 — no end-to-end diagnostic without digging

Even with v0.6.14's per-endpoint WARNINGs, diagnosing "which
category of data is missing" required the user to read 6+
separate log lines. There's no single line that says
"deviceInfo OK, channels empty, status missing, storage empty,
network missing".

## Fix #1 — `_parse_storage` accepts both V5 and V4 shapes

`coordinator.py:_parse_storage` now does:

1. Try V5 direct fields first (`<totalCapacity>` /
   `<usedCapacity>` / `<freeCapacity>` in MB).
2. If none of those are populated, fall back to summing
   `<hddList><HDD><size>` (total bytes) and `<freeSize>` (free
   bytes) across all `<HDD>` elements.
3. Convert bytes → MB using **decimal** (1 MB = 10^6 bytes) for
   parity with V5's MB unit. The values are slightly different
   from GiB math (1024³) but consistency with V5 wins.
4. Aggregate per-HDD `<status>`: any "exception" → top-level
   `status="exception"`.

Backward-compatible: V5 storage XML (where `<totalCapacity>` is
present) is preferred over the V4 sum. If both shapes are
present in the same response (some firmware does this), V5 wins.

## Fix #2 — per-refresh diagnostic summary log

`_async_update_data` now emits one INFO line per refresh:

```
INFO 192.168.10.10 refresh summary: device_info=OK channels=8
     storage=missing network=missing status=missing bitrate=missing
```

The summary format is: `<host> refresh summary: device_info=<v>
channels=<v> storage=<v> network=<v> status=<v> bitrate=<v>`

Each category is one of:
- `OK` — populated (non-empty dict / non-empty list)
- count — when the value is a list (e.g. `channels=8`)
- `missing` — None or empty after parsing

Visible at default HA INFO log level. The user can paste one
single line back to confirm which categories populated vs.
which need investigation, without hunting through other WARNINGs.

## Tests

105/105 tests pass. 10 new tests in `test_v0615_v4_storage.py`:

- `test_parse_storage_v4_single_hdd_sums_to_mb` — single-HDD
  V4 NVR: bytes → MB conversion + total/used/free arithmetic.
- `test_parse_storage_v4_multi_hdd_sums_across_hdds` — multi-HDD
  V4 NVR: per-HDD values summed.
- `test_parse_storage_v4_exception_hdd_aggregates_status` —
  any-HDD exception propagates to top-level status.
- `test_parse_storage_v5_still_works` — regression against the
  V5 path.
- `test_parse_storage_v5_takes_precedence_over_hddlist` —
  when both V5 fields and `<hddList>` are present, V5 wins.
- `test_parse_storage_handles_empty_root` — None returns the
  empty default dict.
- `test_parse_storage_empty_hddlist_falls_back_to_empty` —
  `<hddList/>` with no `<HDD>` children returns None fields
  (the previous parser silently returned `0`; this version
  is explicit).
- `test_v0615_coordinator_emits_refresh_summary_log` —
  structural test that the summary log line is present in the
  coordinator source (catches accidental revert).
- `test_v0615_summary_log_mentions_all_five_categories` —
  structural test that all six categories are named
  (device_info / channels / storage / network / status /
  bitrate).
- `test_v0615_manifest_version_bumped` — manifest pinned
  to 0.6.15.

## What to expect after the upgrade

For the V4 DVR (`192.168.10.10`), the INFO log will include:

```
INFO 192.168.10.10 refresh summary: device_info=OK channels=8
     storage=OK network=missing status=missing bitrate=missing
```

The four storage sensors (存储总量 / 存储使用量 / 存储剩余 /
存储使用率) should populate. Network / status / per-channel
remain missing unless V4 firmware supports those endpoints —
for which we'd need v0.6.16+ to add more endpoint candidates.

For the V5 IPCs (10.18.176.10, 10.18.176.65), expect:

```
INFO 10.18.176.10 refresh summary: device_info=OK channels=1
     storage=missing network=OK status=OK bitrate=OK
```

(if channels list has at least one entry; otherwise `channels=missing`).

If you see `status=missing` or `network=missing` on either
device, paste the full `refresh summary` line back and I'll
add the V4/V5 fallback endpoints for that specific category.
