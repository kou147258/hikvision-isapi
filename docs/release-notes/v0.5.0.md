# v0.5.0 — IPC health sensors (uptime, reboot count, SD card writes, dome thermal)

After auditing the user's live `curl` outputs against `/ISAPI/System/status`
and `/ISAPI/ContentMgmt/InputProxy/channels/<id>/status`, v0.4.0's
parser was wrong (assumed flat `<CPUUsage>` / `<memoryUsage>`
siblings) and v0.4.0 didn't surface the per-channel extended
fields (SD card writes, reboot count, dome thermal stats) that
are already in the responses.

v0.5.0 fixes both:

1. `_parse_system_status` rewritten to handle the actual
   nested `<DeviceStatus><CPUList><CPU><cpuUtilization>…</CPU></CPUList>
   <MemoryList><Memory>…</Memory></MemoryList></DeviceStatus>` schema
   Hikvision's V5.x firmwares actually return, with fallback to the
   legacy flat `<CPUUsage>` / `<memoryUsage>` shape.
2. `_parse_channel_status_extended` extracts the additional fields
   the per-channel status endpoint returns (which we already fetch
   in v0.3.0 but only parsed three booleans from).

## What's new

### Parser fix — nested `<CPUList>` / `<MemoryList>`

| Old (v0.4.0) | New (v0.5.0) |
|---|---|
| flat: `CPUUsage`, `memoryUsage`, `uptime` | nested: `CPUList/CPU/cpuUtilization`, `MemoryList/Memory/memoryUsage`, `MemoryList/Memory/memoryAvailable`, `deviceUpTime`, `totalRebootCount` |
| didn't read `cpuDescription` (CPU model) | reads `CPUList/CPU/cpuDescription` |
| didn't read `memoryAvailable` (free RAM) | reads `MemoryList/Memory/memoryAvailable` |
| didn't read `totalRebootCount` | reads `DeviceStatus/totalRebootCount` |
| didn't read `deviceTemperature` | (intentionally not added — user skipped) |

Backwards compat: if a future or old firmware uses the flat shape
(`<CPUUsage>` / `<memoryUsage>` direct children of `<SystemStatus>`),
the parser falls back to those.

### Per-channel extended fields

The per-channel status endpoint (`/ISAPI/ContentMgmt/InputProxy/
channels/<id>/status`) returns a rich `<DeviceStatus>` block with
`CPUList`, `MemoryList`, and on PTZ cameras a `CameraList` and
`DomeInfoList`. v0.3.0 only parsed `online` / `recordStatus` /
`motionDetection`. v0.5.0 additionally extracts:

- `deviceUpTime` (seconds) — device uptime (not channel-specific)
- `totalRebootCount` — IPC only; absent on NVR per-channel
- `SDCardStatusInfo/videoRewritingTimes` — SD card write cycle count;
  most actionable health indicator (SD cards typically last
  ~3,000-5,000 cycles before failing)
- `Camera/cameraRunTotalTime` — PTZ camera total run time
- `DomeInfo/heatState` / `fanState` — heat dissipation / fan status
  (PTZ domes)
- `DomeInfo/runtimeOverPositiveforty` — cumulative seconds the dome
  operated above 40 °C (thermal stress indicator)

### New sensors

| Key | 中文 | Type / Unit | Source |
|---|---|---|---|
| `device_uptime` | 运行时长 | duration (s) | `/ISAPI/System/status` `deviceUpTime` |
| `device_uptime_hours` | 运行时长（小时） | duration (h) | same, in hours |
| `reboot_count` | 重启次数 | total_increasing int | `totalRebootCount` (IPC) or per-channel |
| `cpu_model` | CPU 型号 | text | `CPUList/CPU/cpuDescription` |
| `sd_card_writes` | SD 卡写入次数 | total_increasing int | `SDCardStatusInfo/videoRewritingTimes` |
| `dome_high_temp_runtime` | 球机高温累计运行 | duration (s) | `DomeInfo/runtimeOverPositiveforty` (PTZ only) |

Note: `reboot_count` and `sd_card_writes` are derived from the
per-channel status endpoint (which Hikvision exposes per channel)
— they're useful for single-channel IPCs. For multi-channel NVRs
each channel's value may differ; the integration reports the first
channel's value for the device-level sensor (call sites can be
extended to per-channel binary_sensors / sensors in a future
release).

## What the user observed (v0.5.0 captures)

| Device | `cpuUtilization` | `memoryUsage` | `memoryAvailable` | `rebootCount` | `sd_card_writes` | `cpuDescription` |
|---|---|---|---|---|---|---|
| 10.18.176.10 (IPC) | 16% | 99 KB | 9696 KB | 40 | 3581 | ARM926EJ-Sid(wb) |
| 192.168.10.9 (NVR) | 7% | 1116 MB | 13 MB | absent | absent | ARMv7 Processor rev 1 (v7l) |
| 192.168.10.10 (NVR) | 0% | 728 MB | 402 MB | absent | absent | "2786.91" (firmware quirk) |

Observations the user can now turn into HA automations:

- **10.18.176.10 SD card has 3,581 writes** — at the typical 3-5k
  failure threshold; the user can set an automation "if sd_card_writes
  > 3500, notify" to replace the card before failure.
- **10.18.176.10 has rebooted 40 times** — high enough to suggest
  firmware or power instability; the user can track this over time.
- **192.168.10.9 NVR memory is at 98.9%** — 1116 MB used / 13 MB
  free. Either a memory leak in firmware, too many concurrent
  streams, or normal baseline. With v0.5.0's `memoryUsage` /
  `memoryAvailable` sensors, the user can graph this over time.
- **192.168.10.10 NTP not synced** — `currentDeviceTime="2004-05-03"`
  placeholder. Already a known issue, not in scope for v0.5.0.
