# v0.6.10 — explicit HTTP/HTTPS scheme selector in config flow

User-reported (2026-09-24 23:02): "端口是 443，443 不是 https 么？海康 ISAPI 不是 http 么？" — they're right. Some Hikvision firmware serves ISAPI over **HTTP on port 443** (a configuration quirk), and some setups use HTTPS on a non-standard port (e.g. behind a reverse proxy).

Pre-v0.6.10 the integration guessed the scheme from port:

```python
self._base_url = f"http{'s' if port == 443 else 'http'}://{host}:{port}"
```

This was fragile. A Hikvision NVR that serves ISAPI on HTTP at
port 443 (a documented configuration on some V5.x firmware with the
web-server in plain-HTTP mode) would refuse our TLS handshake and the
user would have no way to fix it short of editing the integration
source.

## Fix

`CONF_USE_HTTPS = "use_https"` boolean added to the config flow. The
port-based guess becomes the **default**:

- 443 → HTTPS
- any other port → HTTP

The user can override per device in the config-flow form. Setting
is persisted in `entry.data["use_https"]` and propagated to every
`ISAPIClient` instantiation site (config flow validation,
coordinator, camera, switch, button, services).

### Files changed

- `const.py` — `CONF_USE_HTTPS = "use_https"` constant.
- `config_flow.py` — `_default_use_https(port)` helper; new
  optional field in `USER_SCHEMA`; validated and persisted in
  `data={...}`.
- `__init__.py` — read `use_https` from entry data, pass to
  coordinator (defaults to `True` for back-compat).
- `coordinator.py` — `__init__` accepts `use_https` kwarg; stored as
  `self._use_https`; passed to `_make_client()`.
- `isapi_client.py` — already had `use_https: bool = True` parameter
  from v0.6.5; the constructor URL is now
  `f"{scheme}://{host}:{port}"` where scheme derives from
  `use_https`, no longer from port.
- `camera.py`, `switch.py`, `button.py`, `services.py` — pass
  `coordinator._use_https` (or fall back to `entry.data` reading)
  when constructing ISAPIClient.

### Backwards compatibility

Existing v0.6.9 entries in HA store no `use_https` field in their
data. The integration defaults to `use_https=True` when the field is
missing — same behavior as before this release. Users with HTTP-on-443
firmware need to **remove and re-add the integration** (or wait for
an options-flow extension in a future release to switch the scheme
without re-adding).

## Tests

10 new tests in `tests/test_v0610_use_https.py`:

- `test_default_use_https_443_returns_true` — port-based default.
- `test_default_use_https_80_returns_false` — port-based default.
- `test_default_use_https_non_standard_returns_false` — every
  non-443 port defaults to HTTP.
- `test_isapi_client_builds_https_url_when_use_https_true` —
  scheme follows the explicit flag, not the port.
- `test_isapi_client_builds_http_url_when_use_https_false` — the
  bug-fix case: HTTP on port 443.
- `test_isapi_client_use_https_default_is_true` — back-compat:
  omitting the kwarg still uses HTTPS.
- `test_isapi_client_http_on_port_80` — explicit HTTP on 80.
- `test_use_https_constant_defined` — sanity check on
  `CONF_USE_HTTPS`.
- `test_config_flow_user_schema_includes_use_https` — config form
  exposes the toggle.
- `test_coordinator_accepts_use_https_kwarg` — wiring is in place.

86/86 tests pass.

## Compatibility

- No public-API changes for users whose devices already work.
- Users with HTTP-on-443 firmware need to remove and re-add the
  integration to switch the scheme.
- `manifest.json.version` bumped 0.6.9 → 0.6.10.

## Upgrade path

HACS → 已安装的集成 → Hikvision ISAPI Performance → 更新到 v0.6.10 →
重启 Home Assistant. "关于"面板显示 **0.6.10**.

If you removed and re-added the integration during the earlier
debugging (v0.6.6 → v0.6.9) and the device still refuses to
connect, try this version's config flow with `use_https` toggled
off — that should resolve the HTTP-on-443 case.
