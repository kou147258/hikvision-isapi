# v0.6.8 — linear-flow auth retry + UTF-8 safe credentials

Two regressions found in v0.6.7's Basic-auth fallback path:

## 1. Infinite recursion when device keeps returning 401

**Symptom**: User reported a coordinator refresh on `10.18.176.10`
that recursed 371+ times into `_read_response_text` before crashing.
The user's traceback shows the same line number (`357` / `386`)
repeating dozens of times until the traceback cut off.

**Root cause**: v0.6.7's `_read_response_text` was recursive. When
the server kept returning 401 (e.g. wrong password, or password
contained non-UTF-8 bytes that broke Digest computation, or server
misconfigured to reject all auth), each retry response was itself
a 401, which triggered another recursive call. There was no
recursion-depth limit.

**Fix**: Refactored the auth handshake from recursive to a single
linear flow:

- `_read_response_text` handles the **first** response only.
- `_retry_with_digest` issues **one** Digest retry and returns the
  body or raises ISAPIAuthError.
- No code path can recursively call `_read_response_text`.

If Digest retry returns 401, we surface as ISAPIAuthError
immediately — no second retry, no recursion. Same for the
Basic-then-Digest fallback: at most 3 requests (original + Basic +
Digest), then give up.

## 2. UnicodeEncodeError on credentials with surrogates

**Symptom**: User's HA log shows:
```
File ".../isapi_client.py", line 142, in _build_digest_header
    response = _compute_digest_response(
        username, password, method, path, challenge, nc_count, cnonce
    )
File ".../isapi_client.py", line 101, in _compute_digest_response
    f"{username}:{realm}:{password}".encode("utf-8")
UnicodeEncodeError: 'utf-8' codec can't encode characters in
  position 6-7: surrogates not allowed
```

**Root cause**: A password containing lone surrogates (e.g. someone
copy-pasted from a broken UTF-16 source) can't be encoded as UTF-8.
Python's `.encode("utf-8")` rejects it, but v0.6.7's recursion
re-raised the UnicodeError on every retry attempt — combined with
the infinite-loop bug above, this triggered hundreds of useless
Digest computations before crashing.

**Fix**: Pre-validate UTF-8 safety at the top of both
`_read_response_text` and `_read_response_bytes`. If credentials
aren't valid UTF-8, raise `ISAPIAuthError` immediately with a
helpful message ("password has surrogates that can't be encoded for
ISAPI Digest auth. Re-enter the password using only standard ASCII
characters."). No auth retry attempted.

## 3. Bonus: PTZ service "Unable to remove unknown service"

**Symptom**:
```
Logger: homeassistant.core
Unable to remove unknown service hikvision_isapi_performance/ptz_goto_preset
```

**Root cause**: `async_unregister_ptz_service` was called
unconditionally on every entry unload, even when the service
wasn't registered (e.g. device has no PTZ capability, so the
deferred registration listener never fired).

**Fix**: Check `hass.services.has_service(DOMAIN, "ptz_goto_preset")`
before calling `async_remove`. No-op when the service was never
registered.

## Compatibility

- No public-API changes.
- `manifest.json.version` bumped 0.6.7 → 0.6.8.
- Users who never hit the recursion or UnicodeError see no behavior
  change — the linear flow is functionally identical to v0.6.7 for
  successful auth + normal 401 → ISAPIAuthError.

## Upgrade path

HACS → 已安装的集成 → Hikvision ISAPI Performance → 更新到 v0.6.8 →
重启 Home Assistant. "关于"面板应显示 **0.6.8**.

If you were stuck on the infinite-loop / UnicodeError crash and
your password contains non-ASCII text (CJK, emoji with broken
surrogates, etc.), re-enter the password using only standard ASCII
to avoid the auth-computation crash entirely.
