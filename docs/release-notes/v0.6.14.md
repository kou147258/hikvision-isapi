# v0.6.14 — per-endpoint fault tolerance (V4 NVR no longer knocks everything offline)

User reported (2026-09-25 06:37+): after v0.6.13 the IPCs
(`10.18.176.10`, `10.18.176.65`) showed every sensor as "未知" and
the DVR (`192.168.10.10`, DS-7708N-I4, V4.1.18 firmware,
`deviceType=DVR`) showed every entity as "不可用" (unavailable).
The user shared the DVR's raw `<DeviceInfo>` XML response —
formats correctly under v0.6.13's xmlns-strip — so v0.6.13's
fix worked for parsing but the coordinator architecture was
still fragile.

## Root cause — pre-v0.6.14 outer-try fan-out

```python
async def _async_update_data(self):
    try:
        async with self._make_client() as client:
            device_info_xml = await client.get_xml(ISAPI_SYSTEM_DEVICE_INFO)
            status_xml = await client.get_xml(ISAPI_SYSTEM_STATUS)
            # channels / storage / network / streaming — already wrapped,
            # these were OK.
    except ISAPIError as exc:
        raise UpdateFailed(...)        # ← any one failure kills everything
    except ISAPIConnectionError as exc:
        raise UpdateFailed(...)        # ← ditto
    except ISAPIAuthError as exc:
        raise UpdateFailed(...)
```

`deviceInfo_xml` and `status_xml` were top-level calls with no
isolation. If Hikvision firmware returns HTTP 4xx for
`/ISAPI/System/status` — common on **V4 NVRs / DVRs** like the
`DS-7708N-I4` (V4.1.18 firmware, `deviceType="DVR"`) — the call
raises `ISAPIError`, the outer `except ISAPIError` catches it,
the coordinator raises `UpdateFailed`, and HA marks **every**
entity for the device unavailable. The other endpoints (which
might be returning perfectly valid data) never get a chance.

The same problem in reverse for the IPCs: parsing works in
v0.6.13, but if any one endpoint fails on V5 firmware, the IPC
entities go unavailable for that single failure.

## Fix — v0.6.14 per-endpoint fault-tolerant fetchers

The coordinator exposes one helper per endpoint, each with its
own try/except that logs a WARNING/INFO and continues:

- `_fetch_device_info(client)` → returns `(xml, parsed_dict)`;
  XML = None if it failed.
- `_fetch_system_status(client)` → same shape; falls back to
  sensible empty defaults (deviceStatus="Unknown", cpu/mem=0)
  if status XML fails.
- `_fetch_channels(client, primary, alt)` → tries both, returns
  whichever wins.
- `_fetch_storage(client)` → returns storage XML or None
  (IPC has no storage; V4 NVRs may not have `/ContentMgmt/storage`
  so we already have a `/System/Storage/hardDisks` fallback).
- `_fetch_network_interfaces(client)` → returns XML or None.
- `_fetch_streaming(client)` → returns XML or None.

`_async_update_data` now looks like:

```python
# deviceInfo + status — critical but not fatal
try:
    async with self._make_client() as client:
        device_info_xml, device_info = await self._fetch_device_info(client)
        status_xml, system_status = await self._fetch_system_status(client)
except ISAPIConnectionError as exc:
    raise UpdateFailed(f"network error talking to {self._host}: {exc}")
except ISAPIAuthError as exc:
    raise UpdateFailed(f"authentication failed for {self._host}: {exc}")
# ↑ NO outer "except ISAPIError" — every 4xx is per-endpoint now.

# device-type routing, channel + storage + network + streaming —
# all isolated in their own client block.
async with self._make_client() as client:
    channels_xml, ... = await self._fetch_channels(client, primary, alt)
    storage_xml = await self._fetch_storage(client)
    network_xml = await self._fetch_network_interfaces(client)
    streaming_xml = await self._fetch_streaming(client)

# Parsing: empty / missing data → empty defaults, no exceptions.
```

The only failure modes that still raise `UpdateFailed` are:

1. `ISAPIConnectionError` from the very first deviceInfo fetch
   (we can't even reach the device — nothing useful to display).
2. `ISAPIAuthError` from the first deviceInfo fetch
   (credentials wrong or user has no ISAPI access at all).

A V4 DVR's `/ISAPI/System/status` returning HTTP 404 will now
log:

```
WARNING (Recorder) NVR endpoint /ISAPI/System/status failed: ...
INFO Detected DS-7708N-I4 at 192.168.10.10 as deviceType='DVR'
```

…and the refresh continues with empty status. The device-level
sensors (model, firmware, default gateway) populate normally
because deviceInfo succeeded. CPU/memory/uptime sensors show
"Unknown" / 0 — graceful degradation rather than unavailable.

## Diagnostic recipe (what you should see now)

After v0.6.14 + HA restart, the integration logs per refresh will
look like one of:

**Successful V4 DVR:**
```
INFO  Polling http://192.168.10.10:80 (...)
INFO  Detected DS-7708N-I4 at 192.168.10.10 as deviceType='DVR'
       (routing channels endpoint to /ContentMgmt/InputProxy/channels, ...)
INFO  192.168.10.10 channels primary /ContentMgmt/InputProxy/channels
       failed (HTTP 404); trying /Streaming/channels
INFO  192.168.10.10 channels alt /Streaming/channels also failed
       (HTTP 404); channels list will be empty
INFO  192.168.10.10 /ISAPI/ContentMgmt/storage failed: HTTP 404
```

**Successful IPC:**
```
INFO  Polling http://10.18.176.10:80 (...)
INFO  Detected DS-2CD2... at 10.18.176.10 as deviceType='IPCamera'
       (routing channels endpoint to /Streaming/channels, ...)
```

The entity state will be:

- DVR: device-level sensors (model / firmware / default gateway)
  populated; CPU / memory / storage / channels = 0/Unknown/empty
  (V4 firmware doesn't serve those endpoints).
- IPC: device-level + camera-image + per-channel all populated
  (assuming `/Streaming/channels` returns at least channel 1).

## Compatibility

- No public-API changes.
- `manifest.json.version` bumped 0.6.13 → 0.6.14.
- No new dependencies.
- Behavior change for V4 NVRs / DVRs: previously failed at the
  first 4xx; now continues and emits entity state when possible.
- Behavior change for any device: entities might now show partial
  data (some fields populated, others "Unknown") instead of
  flipping to unavailable.

## Why this is the right architecture

Coordinators must always return SOMETHING when possible. A
multi-endpoint refresh where any one endpoint's 4xx flips the
whole device to unavailable defeats the purpose of having
multiple endpoints. The right boundary is:

- "Can I reach the device at all?" → `UpdateFailed` (network).
- "Are credentials wrong?" → `UpdateFailed` (auth).
- "Is one specific endpoint broken on this firmware?" →
  log + empty field, refresh continues.

v0.6.14 enforces that boundary at the helper-method level so
future endpoint additions can't accidentally revert to the
"single endpoint failure = whole device offline" pattern.
