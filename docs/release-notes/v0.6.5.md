# v0.6.5 — fix NameError on auth + duplicate sensor unique IDs

Two regressions reported by the user (2026-09-24 21:44):

1. **Coordinator NameError on first 401 / 403** —

   ```
   Traceback (most recent call last):
     File "...coordinator.py", line 569, in _async_update_data
       except ISAPIAuthError as exc:
             ^^^^^^^^^^^^^^
   NameError: name 'ISAPIAuthError' is not defined. Did you mean: 'ISAPIError'?
   ```

   `coordinator.py` imports `ISAPIConnectionError` / `ISAPIClient` /
   `ISAPIError` from `.isapi_client` but never `ISAPIAuthError`. The
   `except ISAPIAuthError as exc:` clause then references an undefined
   name on the first 401 / 403 from a real device. Same pattern as
   the v0.6.3 bug in `_read_response_text` — a free-variable NameError
   instead of being caught and converted to `UpdateFailed`. Effect:
   the coordinator's `_async_update_data` always raised NameError
   after the first auth challenge, so every device in the user's fleet
   (10.18.176.10, 10.18.176.65, 192.168.10.10) reported "Unexpected
   error fetching ..." in HA logs, and all entities were marked
   `unavailable`.

   **Fix**: add `ISAPIAuthError` to the `from .isapi_client import ...`
   line. The existing except clause now catches real auth errors and
   converts them to `UpdateFailed`, allowing HA to surface the auth
   issue cleanly instead of crashing the whole coordinator.

2. **Duplicate sensor unique IDs** —

   ```
   Platform hikvision_isapi_performance does not generate unique IDs.
     ID 01M39THEENHTA8XD6A4PMSBHXK_device_uptime already exists -
     ignoring sensor.uptime_3
     ID 01M39THEENHTA8XD6A4PMSBHXK_reboot_count already exists -
     ignoring sensor.reboot_count
     ID 01M39TJ1J04R5SC2V2ZWKFP3Y0_device_uptime already exists -
     ignoring sensor.uptime_5
     ID 01M39TJ1J04R5SC2V2ZWKFP3Y0_reboot_count already exists -
     ignoring sensor.reboot_count_2
   ```

   The `SENSORS` tuple in `sensor.py` had two pairs of entries with
   the same `key` field:
   - `device_uptime` once from `/ISAPI/System/status`
     (`value_fn = d.system_status.get("uptime")`),
   - `device_uptime` once from per-channel status
     (`value_fn = _first_channel_field(d, "uptime")`),
   - same pattern for `reboot_count`.

   Each pair produced the same `unique_id` (`{entry_id}_device_uptime`
   / `{entry_id}_reboot_count`), HA silently dropped the second one
   with a warning, and the user saw only the device-level entity
   instead of both readings. The v0.5.0 commit introduced these
   duplicates without testing in HA, so the bug shipped through
   v0.6.0 → v0.6.4 unnoticed.

   **Fix**: rename the per-channel-derived entries to `channel_1_uptime`
   and `channel_1_reboot_count` with names `通道 1 运行时长` / `通道 1 重启次数`
   (matches the existing `通道 1 平均码率` naming pattern). The
   device-level entries keep their original keys / names, so existing
   user entity-registry entries (already on `device_uptime` /
   `reboot_count`) are preserved. Users get one extra sensor per
   NVR showing the per-channel IPC's uptime / reboot count — useful
   for multi-channel NVRs where channel data differs from NVR data.

## Tests

7 new tests in `tests/test_v065_fixes.py`:
- `test_coordinator_imports_ISAPIAuthError` — the import must
  include `ISAPIAuthError`
- `test_coordinator_except_clause_references_ISAPIAuthError` —
  the except clause is still there
- `test_sensor_descriptions_have_unique_keys` — no duplicate `key`
- `test_sensor_descriptions_have_unique_translation_keys` — no
  duplicate `translation_key`
- `test_channel_1_sensors_exist_with_unique_keys` — the per-channel
  variants exist
- `test_device_uptime_and_reboot_count_have_single_definition` —
  the originals appear once each
- `test_sensor_source_has_no_duplicate_key_string` — source-level
  regression guard

Source-level parsing (rather than importing `SENSORS`) keeps the
tests robust against HA-stub churn — they assert on the literal
strings the human author wrote, not the resolved dataclass instances.

`tests/conftest.py` got two small additions: `UnitOfTime.HOURS` and
`UnitOfInformation` constants (used by sensor descriptions).

59/59 tests pass.

## Compatibility

- No public-API changes.
- Existing entity-registry entries (from any v0.6.x) for
  `device_uptime` / `reboot_count` keep their slot and don't migrate.
- The new `channel_1_uptime` / `channel_1_reboot_count` entities
  appear as fresh additions; users with multi-channel NVRs will
  see one per channel after the next HACS update.

## Why a hotfix so soon after v0.6.4

v0.6.3 → v0.6.4 was a docs-only change (drop third-party repo
references); v0.6.5 is the code fix that the v0.6.3 docs-only release
papered over. Without v0.6.5, the integration loads but every sensor
is `unavailable` and the coordinator crashes on first auth challenge.

## Upgrade path

HACS → 已安装的集成 → Hikvision ISAPI Performance → 更新到 v0.6.5 →
重启 Home Assistant. The `device_uptime` / `reboot_count` entities
you already have stay; you get two new entities
(`channel_1_uptime`, `channel_1_reboot_count`) per IPC channel that
the per-channel status endpoint reports on. The "Unavailable" state
should clear on the next coordinator refresh (≤ scan_interval).
