# v0.6.12 — httpx-based ISAPI client + per-channel connection error handling

User reported (2026-09-24 23:30+): v0.6.11 still showed all 24 entities
"unavailable" after re-adding the integration, no useful logs visible in
default HA log view, and device-type-based endpoint routing "still not
working".

This release fixes two latent bugs that had been masked by earlier
defensive code:

## Root cause #1 — hand-rolled Digest auth doesn't cover all algorithm variants

`isapi_client.py` v0.1.0 → v0.6.11 implemented RFC 2617 Digest auth
manually after aiohttp 3.8+ removed its built-in `DigestAuth`. The
hand-rolled implementation computed MD5 with `qop=auth` only.

V5.7+ firmware (and some mid-cycle V5.5 firmware) advertises
`algorithm=SHA-256` or `algorithm=MD5-sess` in the Digest challenge.
Our implementation silently fell back to MD5 anyway, computed a wrong
`response` value, and the server rejected the request with HTTP 401.
The coordinator caught that as `UpdateFailed` and HA logged
"Authentication failed" at WARNING level — which the user saw, but
**only when they went looking**. Pre-v0.6.12 the actual scheme/port
attempt was DEBUG-only, so the user couldn't see what was happening
without setting the logger to DEBUG.

## Root cause #2 — per-channel loop didn't catch ISAPIConnectionError

The coordinator's per-channel status loop caught
`(ISAPIError, ISAPIAuthError)` but **NOT** `ISAPIConnectionError`.
A transient network blip on a single per-channel fetch raised the
connection error unhandled, propagated out of `_async_update_data`,
and HA marked **every** entity for the device unavailable. The single
WARNING that resulted didn't make it obvious which channel triggered
the cascade.

## Fix #1 — httpx-based client with built-in DigestAuth + BasicAuth

`isapi_client.py` v0.6.12 now uses `httpx.AsyncClient` + the
battle-tested `httpx.DigestAuth` / `httpx.BasicAuth` classes.

httpx's `DigestAuth` covers every algorithm variant Hikvision ships
(MD5, SHA-256, MD5-sess) and handles nonce replay correctly. The
connection-error translation is also cleaner — every transport
exception (ConnectError, ReadTimeout, PoolTimeout, etc.) becomes
`ISAPIConnectionError`.

The auth flow now mirrors `curl --anyauth`:

1. Send with `auth=DigestAuth`.
2. If `401` AND the `WWW-Authenticate` header does NOT contain
   `digest` anywhere (e.g. an old DS-2CD8464F-EI returns
   `Basic realm="IPCamera"`), retry the same request with
   `auth=BasicAuth`. If the Basic attempt succeeds (status != 401),
   switch `self._auth` permanently for the rest of the session.
3. If the device offers Digest and still returns 401 (wrong password),
   do **NOT** retry Basic — that would burn another failed login
   toward Hikvision's account-lockout policy. Surface `ISAPIAuthError`
   after one digest retry.

`aiohttp` is no longer used and has been removed from
`manifest.json.requirements`.

## Fix #2 — per-channel loop now catches `ISAPIConnectionError`

```python
# coordinator.py: v0.6.12
except (
    ISAPIError, ISAPIAuthError, ISAPIConnectionError,
) as exc:
```

A transient network blip on channel 7 of an NVR now logs at DEBUG
and the loop continues with the remaining channels instead of taking
down the entire refresh.

## Additional improvements

- **INFO-level refresh log**: a single line per poll attempt shows
  the scheme, host, port, and entry ID prefix. Users no longer need
  DEBUG logging to confirm the integration is even running.

- **INFO-level device type routing log**: after parsing
  `deviceInfo.deviceType`, the chosen channels + status endpoints
  are logged at INFO. This makes "device type routing isn't working"
  immediately answerable from default HA logs.

- **`ch["online"]` priority fixed**: pre-v0.6.12, a fresh per-channel
  `online=False` would lose to a stale `online=True` from the
  channel-list (because of the Python `or` short-circuit). The
  per-channel endpoint now takes priority.

## Diagnostic recipe (if v0.6.12 still doesn't work)

If after upgrading you still see entities unavailable:

1. Settings → System → Logs. The integration name is
   `custom_components.hikvision_isapi_performance` (or search for
   "Hikvision").
2. Filter to that logger and read the most recent refresh:
   - `Polling http://10.18.176.10:80 (entry_id=01M39TH…xx)`
   - `Detected DS-2CD2143G2-I at 10.18.176.10 as deviceType='IPCamera' …`
3. If you see `Network error talking to 10.18.176.10: …`,
   the device is unreachable from the HA host. Try the manual
   `curl` test (next bullet).
4. If you see `Authentication failed for 10.18.176.10: …`, the
   username/password is wrong (or the user account lacks privileges
   for ISAPI — Hikvision allows per-user endpoint ACLs).

```bash
# Manual reachability test (run on the HA host):
curl -v --anyauth --user 'admin:YOUR_PASSWORD' \
  http://YOUR_HOST:80/ISAPI/System/deviceInfo
```

`--anyauth` matches the integration's smart fallback. If this curl
returns XML, v0.6.12 should also work.

If curl returns `401` even though the password is correct, the user
account on the device has been configured without ISAPI privileges —
log into the device's web UI, find the user-management section, and
make sure the account has `Remote: Permission of Get/DigestAuth` (or
the equivalent "Operator" / "Administrator" privilege).

## Tests

79/79 tests pass. 14 obsolete aiohttp-targeted tests
(`test_v063_digest_retry.py`, `test_v067_basic_auth.py`,
`test_v068_no_recursion.py`) removed and replaced with 11 new
httpx-MockTransport-based tests in `test_isapi_client.py` and
`test_v0612_httpx.py`. The new tests pin:

- Digest challenge on first 401 triggers exactly one retry with
  `Authorization: Digest …`.
- 401 with no `digest` in challenge triggers a Basic retry and
  switches the client to Basic permanently.
- 401 with `digest` in challenge does NOT trigger a Basic retry
  (preserves Hikvision's lockout-policy contract).
- Network errors surface as `ISAPIConnectionError` (not
  `ISAPIAuthError`, which would mislead the user into thinking
  credentials are wrong).
- `manifest.json.version == "0.6.12"` and
  `requirements` includes `httpx>=0.27.0,<1.0.0`.
- The coordinator's per-channel loop references `ISAPIConnectionError`
  at least twice (primary + alt-status exception handlers).

## Compatibility

- No public-API changes to `ISAPIClient` (still async-context-manager
  with `get_text` / `get_bytes` / `get_xml` / `put_text` / `put_xml`).
- `manifest.json.version` bumped 0.6.11 → 0.6.12.
- `aiohttp` removed from `requirements` (no longer used).
- `httpx>=0.27.0,<1.0.0` added to `requirements` (HA Core 2024+
  ships Python 3.12 with httpx 0.27 already in its stdlib-adjacent
  deps; this pins the minimum version explicitly).

## Upgrade path

HACS → 已安装的集成 → Hikvision ISAPI Performance → 更新到 v0.6.12 →
**重启 Home Assistant** (so HACS picks up the new `httpx` requirement
and HA's component registry re-loads the integration).

Existing entries continue to work — the v0.6.11 defaults (HTTP, port 80)
are still correct for V5.x firmware. The credentials, scheme, and port
stored in `entry.data` are unchanged.
