# v0.6.3 — hotfix: NameError on first 401 digest challenge

Reported by user (HA logs, 2026-09-24 21:02): config-flow connection
to `10.18.176.10:443` and `192.168.10.10:443` failed with
`NameError: name 'content_type' is not defined` from
`isapi_client.py:294` immediately on the first 401 challenge. Every
real Hikvision device on the user's fleet triggers this — the digest
auth retry path crashed before any deviceInfo was ever returned, so
the integration could not be added at all.

## Root cause

In `isapi_client.py`, the GET / PUT entry point
(`ISAPIClient._request`) accepts a `content_type` keyword argument
that is only meaningful for PUT bodies:

```python
async def _request(self, method, path, *, expect_json, body=None,
                   content_type=None):
    ...
    headers["Content-Type"] = content_type
    ...
    return await self._read_response_text(resp, path, method)
```

The auth-handshake logic lives inside
`_read_response_text(self, resp, path, method)`, which does NOT
receive `content_type` as a parameter. When Hikvision returns a 401
with a Digest challenge, the retry code path was:

```python
headers={"Authorization": auth_header, **(
    {"Content-Type": content_type}
    if content_type else {}
)},
```

`content_type` here is a free variable that resolves to whatever is
in scope at the call site. Since `_read_response_text` has no such
parameter, Python raises `NameError` instead of retrying. For GET
requests `content_type` is always None at the call site, so the bug
was masked by the `if content_type else {}` short-circuit only when
the calling frame happened to have a `content_type` in scope (it
didn't — the bug was always present).

## Why tests missed it

The existing tests stub the `WWW-Authenticate` challenge parser and
only exercise the no-auth-required path. No test in v0.6.0–v0.6.2
ever hit the digest handshake against a real-looking challenge, so
the free-variable NameError was never caught.

## Fix

Thread `body` and `content_type` through `_read_response_text` as
keyword arguments so the digest retry can replay them faithfully:

```python
return await self._read_response_text(
    resp, path, method, body=body, content_type=content_type,
)
```

```python
async def _read_response_text(
    self, resp, path, method, *,
    body=None, content_type=None,
) -> str:
    ...
    retry_headers = {"Authorization": auth_header}
    if content_type:
        retry_headers["Content-Type"] = content_type
    async with self._session.request(
        method, url, data=body, headers=retry_headers,
    ) as retry_resp:
        return await self._read_response_text(
            retry_resp, path, method,
            body=body, content_type=content_type,
        )
```

The retry now correctly:
- Sends the Authorization header on the second request.
- Replays the original body bytes for PUTs (rebuke / recording /
  PTZ presets all carry XML bodies — dropping them on retry would
  silently no-op the write).
- Replays the original `Content-Type` so Hikvision parses the body
  the same way as the first attempt.

A subtle side-effect fix: the pre-v0.6.3 retry code did
`data=await resp.read()` which consumes the 401 response body and
uses it as the PUT body — wrong on two counts (401 body is empty,
and even if non-empty it isn't what we wanted to send). The v0.6.3
retry uses `data=body` (the original kwargs body), which is what
the auth-protected PUT endpoint actually expects.

## Tests

3 new tests in `tests/test_v063_digest_retry.py` (52 total now
across the suite):

- `test_get_text_digest_retry_does_not_raise_name_error` —
  fakes a 401 + Digest challenge followed by a 200, asserts the
  retry carries the Authorization header. Pre-fix this raised
  NameError; post-fix it returns the body.
- `test_get_text_unrecognized_www_authenticate_raises_auth_error` —
  Basic-auth challenge must surface as ISAPIAuthError, not crash.
- `test_put_text_digest_retry_preserves_body_and_content_type` —
  retry of a digest-protected PUT replays the body and
  Content-Type header.
