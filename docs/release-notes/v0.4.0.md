# v0.4.0 — NVR-aware snapshot endpoint + storage fallback for old V4 NVRs

v0.3.0 used `/ISAPI/Streaming/channels/{id}/picture` for **every**
device, which Hikvision IPCs accept but NVRs (including the user's
DS-7708-I4 / DS-8632-I8 fleet) reject with HTTP 400. The user would
have seen all NVR-mounted IPC cameras as failed snapshots.

v0.4.0 fixes this by routing snapshot requests based on the
device's `deviceType` field (parsed from `/ISAPI/System/deviceInfo`):

- **IPC** (`deviceType=IPCamera`) → `/ISAPI/Streaming/channels/{id}/picture`
- **NVR / DVR** (`deviceType=NetworkVideoRecorder` / `DVR`) →
  `/ISAPI/ContentMgmt/StreamingProxy/channels/{id}/picture`
  (the NVR-side proxy endpoint that grabs a snapshot of a mounted
  IPC channel).

## What's new

### 1. NVR / IPC / DVR device-type detection

`coordinator._parse_device_info` already extracts `deviceType` from
the `<deviceType>` element. v0.4.0 adds a new
`normalize_device_type(raw)` helper that maps Hikvision's free-form
text to a canonical value:

| Raw `deviceType` | Normalized |
|---|---|
| `IPCamera` / `ipc` / `IPC` / empty / unknown | `ipcamera` |
| `NetworkVideoRecorder` / `nvr` / `NVR` | `networkvideorecorder` |
| `DVR` / `DigitalVideoRecorder` | `dvr` |

The normalized value is exposed on `HikvisionISAPIData.device_type` and
also cached on the coordinator (`self.device_type`) for direct access.

### 2. Camera platform routes by device type

`HikvisionISAPICamera.async_camera_image` now picks the snapshot
endpoint based on `coordinator.data.device_type`:

```python
if device_type == DEVICE_TYPE_NETWORK_VIDEO_RECORDER:
    path = f"/ISAPI/ContentMgmt/StreamingProxy/channels/{self.channel_id}/picture"
else:  # IPC or DVR
    path = f"/ISAPI/Streaming/channels/{self.channel_id}/picture"
```

This is the fix for the v0.3.0 regression where NVR cameras
showed as failed.

### 3. Storage endpoint fallback for old V4 NVRs

`/ISAPI/ContentMgmt/storage` is the modern endpoint. Old V4 NVRs
(`DS-7708-I4`, `DS-8632-I8`) don't implement it — the legacy
endpoint is `/ISAPI/System/Storage/hardDisks`. v0.4.0's
`coordinator._async_update_data` tries `ContentMgmt/storage` first;
on a 404 (`ISAPIError.status_code == 404`), it falls back to
`System/Storage/hardDisks`. Both endpoints' XML shapes are similar
enough that the existing `_parse_storage` parses either.

### 4. `ISAPIError.status_code` attribute

The `ISAPIError` and `ISAPIAuthError` exceptions now carry a
`status_code` attribute set from the response. The coordinator's
storage fallback uses this to discriminate 404 (endpoint missing —
try alternate) from other 4xx/5xx (real error — propagate).

## Known limitations

- **CPU / memory / temperature on old V4 NVRs** — `/ISAPI/System/status`
  returns `notSupport` on `DS-7708-I4` / `DS-8632-I8`. The
  `cpu_usage` / `memory_usage` / `uptime` / `device_status` sensors
  will show `unknown` on these NVRs. This is a firmware limitation;
  ISAPI simply doesn't expose CPU/memory on these models.
- **Device internal temperature** — not directly exposed by ISAPI on
  any model. Only thermal cameras (with `/ISAPI/Thermal/...`
  endpoints for scene temperature) or SDK / SNMP paths give
  device-internal temperature.
- **Storage on old NVRs that have no ISAPI at all** — if a NVR
  returns errors on both `ContentMgmt/storage` and
  `System/Storage/hardDisks`, the storage sensors show
  `unknown`.
